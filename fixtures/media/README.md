# Media Fixtures

`clean-relay-loop-long.ts` is a small FFmpeg-generated MPEG-TS asset used
whenever a lab scenario needs a stream that real FFmpeg can probe and remux.

Scanner-oriented stream tests still use the minimal synthetic TS packet
sequence generated by `scripts/srv1/provider_sim.py`.

## `clean-relay-loop-long.ts`

Used by `provider-a.json`, `provider-clean-relay.json`,
`provider-stream-health.json`, `provider-web-hls.json`, and
`scenarios/core/clean-relay-inprocess-replay.yaml` (Stage A2 item 7,
CLEAN-RELAY-05) — any scenario that needs a real, FFmpeg-probeable MPEG-TS
stream longer than a couple of seconds.

Generated with the same tooling/lavfi sources as the playback-contract
assets above, no third-party content embedded:

```
docker run --rm -v <repo>/fixtures/media:/out --entrypoint ffmpeg \
  m3undle:branch-main -y \
  -f lavfi -i testsrc2=size=640x360:rate=25 \
  -f lavfi -i sine=frequency=1000:sample_rate=48000 \
  -t 30 -c:v libx264 -preset veryfast -pix_fmt yuv420p -g 50 \
  -c:a aac -b:a 128k -f mpegts /out/clean-relay-loop-long.ts
```

| File | Container and streams | Duration | Bitrate | SHA-256 |
|---|---|---|---|---|
| `clean-relay-loop-long.ts` | MPEG-TS; H.264 (25fps, GOP 50) and AAC; 1000 Hz tone | 30.021 s (ffprobe) | ~928 kbps (ffprobe) | `ef9d231a7408ea1d978d1a4a1673046ce435126fcc8dbe476837611ee01c6fce` |

FFmpeg version: 6.1.1-3ubuntu5 (same image/build as the playback-contract
assets above). Container digest at generation time (backfilled 2026-07-24
alongside the Stage A6 batch below, same `m3undle:branch-main` tag/build):
`sha256:31430990f916e3c4fab706f8d6a1a2c71a7125c487a6286c366d5b6400123eff`.
PID layout: PAT on PID 0, PMT on PID 4096 (`0x1000`), video on PID 256
(`0x100`), audio on PID 257 (`0x101`) — same FFmpeg mpegts-muxer defaults as
every other fixture in this file. Expected timestamp range: 1.4587s →
31.48s (`ffprobe` `start_time` + `duration`).

**Why this replaced `clean-relay-loop.ts` (2026-07-24, retired):** the
original 3.02s clip was committed with no recorded generation command,
generator version, or hash anywhere in history (Stage A6 backfill debt,
`docs/historical/M3Undle_Provider_Simulator_Implementation_Plan.md`) — only a prose
description in this file. Rather than reconstruct a plausible-but-unverifiable
command for a file whose real provenance was never recorded, every consumer
was moved onto this fully-documented asset instead and the old file deleted.
This was also a real functional fix, not just a provenance one: several
fixtures played the short clip for far longer than its own duration per
connection, looping it multiple times *during normal, fault-free playback*
via the simulator's byte-modulo wraparound. Against `feature/continuous-
stream-test` (which added `-copyts` to the FFmpeg clean-remux relay), every
one of those ordinary loop-backs looked like a genuine "provider restarted
from byte zero," destabilizing relay startup broadly (`HDHR-RELAY-01`,
`CLEAN-RELAY-02` both failed on that branch until the swap). `chunk_count`
in each consuming fixture is kept low enough that no connection loops this
longer file even once. Confirmed with a full regression on both `main`
(unaffected) and `feature/continuous-stream-test` (105/105 passing
afterward).

## Stage A6 initial fixtures (2026-07-24)

The plan's Stage A6 "Initial Fixtures" list has ten items. Two are already
satisfied without a new file and are not duplicated here:

- **Clean loop fixture** → `clean-relay-loop-long.ts` above.
- **Known PAT/PMT/PID layout** → `$M3UNDLE_SIMULATOR_ENGINE_DIR/src/provider_sim.py`'s
  minimal synthetic TS packet sequence (PAT on PID 0, PMT on PID 100, video
  on PID 256 — see the comments around `_TS_SEQUENCE` in that file) already
  has a fixed, documented layout. It's generated procedurally per-request rather
  than stored as a file, which satisfies the requirement without a
  redundant static asset.

The remaining eight map onto seven new files below (`constant-tone.ts`
deliberately covers two list items — see its row). None of these are wired
into a `run_stream_*_scenarios.py` runner yet; that's scenario-authoring
work for whichever stage actually needs each fault/format, not part of
Stage A6's own exit gate (fixtures existing and being reproducible).

All seven use the same FFmpeg 6.1.1-3ubuntu5 build as the assets above, the
same `testsrc2`/`sine` lavfi sources, and no third-party content. Generated
with (per-file `-f lavfi`/output arguments shown in the table further
below):

```
docker run --rm --user "$(id -u):$(id -g)" -v <repo>/fixtures/media:/out \
  --entrypoint ffmpeg m3undle:branch-main -y \
  -f lavfi -i testsrc2=size=<WxH>:rate=25 \
  -f lavfi -i sine=frequency=<HZ>:sample_rate=48000 \
  -t <SECONDS> [-vf drawtext=...] \
  -c:v libx264 -preset veryfast -pix_fmt yuv420p -g <GOP> \
  -c:a aac -b:a 128k -f mpegts /out/<name>.ts
```

`--user "$(id -u):$(id -g)"` matters on Linux hosts: without it the
container's root user writes the bind-mounted output as root, leaving files
the host user can't later `chown` without sudo (hit and worked around while
generating this batch).

**Fields shared by all seven** (the plan's "Every Fixture Must Record"
checklist items that don't vary per file):

- **Generator version:** FFmpeg 6.1.1-3ubuntu5, `libx264`/`aac` built-in
  encoders, `testsrc2`/`sine` lavfi sources.
- **Container digest:** `m3undle:branch-main` image at generation time,
  `sha256:31430990f916e3c4fab706f8d6a1a2c71a7125c487a6286c366d5b6400123eff`
  (`docker inspect --format '{{.Id}}'`). This is a local dev tag, not a
  published reference — matches every fixture generated this way so far;
  revisit once Stage A8 publishes a versioned public build image.
- **PID layout:** PAT on PID 0 (standard), PMT on PID 4096 (`0x1000`,
  FFmpeg mpegts muxer default), video (when present) on PID 256 (`0x100`),
  audio on PID 257 (`0x101`) when both streams are present, or PID 256 when
  audio is the only stream (`constant-tone.ts`) — confirmed via `ffprobe
  -show_entries stream=id`.
- **Licensing/origin:** 100% synthetic, generated from FFmpeg's built-in
  `testsrc2`/`sine` lavfi sources — no third-party or real provider content
  embedded in any of the seven files.

**On `timestamp-rewind-loop.ts` specifically:** this file is *deliberately*
shorter than any reasonable `chunk_count`-driven connection duration — the
opposite of the `clean-relay-loop.ts` lesson above. It exists so a scenario
that *wants* to trigger the simulator's byte-modulo loop-restart (a real
"provider restarted from byte zero" timestamp rewind, as a fault to detect)
can do so on purpose and document that intent, rather than a normal "clean"
fixture accidentally looping because it's too short for its `chunk_count`.
**Do not** point a clean/fault-free scenario at this file — use
`clean-relay-loop-long.ts` for that, exactly the mistake this file's
existence is meant to make easy to avoid.
